# 打包激活设计史（工具 + 技能 + 文件整包）

> 本地设计留档，不对外、不进规则册。相关实现：`dsh-tool-activator`。

## 一、最初的想法

一次激活 = **工具 + 技能 + 文件**整包上桌。规则、口径、细节由记忆插件补（三张卡 + 书签 + 检索）。

目标是省来回：不要出现「工具装了但缺配置」「技能有了但脚本不在」「文件放在别处，模型不知道」这种半成品状态。用户点一次，该有的全有。

## 二、为什么没成

**「整包」是原子承诺，但激活时只校验 id。**

- 校验的是「工具 id 在注册表里吗、技能 id 在目录里吗」；
- 包里引用的文件（脚本、模板、配置、数据）**没有清单，激活时也不核**；
- 缺一个文件不报错，表现为「已激活，但一调用就空转」——比报错更难查，因为它看起来是成功的；
- 于是出现「漏工具、漏文件」：分组是白名单，没进组的悄悄被藏；文件缺失则悄悄不工作。

结论：**只要漏一个文件就不好使，而且坏得无声**。这条路后来被放弃。

## 三、现在的做法

- 启用改由**技能组**驱动，按任务当场决定加载什么；
- 工具目录只当**检索表**：列出「有哪些工具、大概干什么」，真正细节在激活后拿到的 schema 里；
- 2026-11-21 把目录从「每个工具全量描述」（163 个 / 约 99,842 字符）压成「identifier + 一句话」（约 17,800 字符，省 82%），成员一个不动——因为按分组裁剪正是当年漏工具的老路。

代价：每件事多一步激活。收益：不会静默坏。

## 四、如果重建这条路，要补的是「包清单」

```
包 manifest
├── tools[].identifier      激活时查注册表
├── skills[].id             激活时查技能目录
├── files[]                 每个路径：存在？大小非 0？可读？
├── requires[]              依赖的配置项，缺了有没有默认值
└── version / checksum      升级时对照，避免新旧混装
```

判定规则：

1. **全有才算激活成功**，缺项直接失败并点名缺什么（「缺 scripts/run.py」），不许「看起来成功」；
2. 清单随包一起发版、一起换；
3. 激活回执里带一份「已核项目」列表，出问题能定位到具体一项。

这才是「整包」该有的样子：原子性由清单保证，不是由信任保证。

## 六、未完成即弃：工具四态（2026-11-20 定，未落地）

昨天定过一套工具状态模型，**没做完就换插件了**，这里留个来龙去脉，免得以后翻代码找不到：

| 状态 | 语义 | 落地情况 |
|---|---|---|
| 启用 | 常驻可用，不进目录 | 半有：只有插件自注册的基础工具是这种 |
| 关闭 | 收起、只留目录条目 | 有：等价于「未激活」 |
| 热载 | 用到时激活 | 有（`activate_tools`），但**激活后下一轮才生效** |
| 屏蔽 | 永久不出现，**只能由丹阳开** | **无**：activator 没有这个概念，我们也没落配置 |

为什么弃：换成 `dsh-tool-activator` 之后，工具的可见与激活由它接管；再自建一套状态层会跟它的目录打架。而且这套状态当初就是为「工具组整包」设计的，工具组方案本身已经被否（见第四节）。

**后果与补救**：唯一真正缺失的是「屏蔽」（只有丹阳能开的永久隐藏）。要补的话走我们自己的名单，不动别人的插件：`~/.dsh/profiles/desktop/tool-blocklist.json`，我只在读、不改；用某个工具前先查，命中就直说「被屏蔽了，要开你说一声」。
